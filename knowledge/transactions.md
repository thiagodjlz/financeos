# Lancamentos / Transacoes

Fonte: `backend/src/main/java/br/com/financeos/transactions/`.

## Campos

`userId, categoryId, transactionDate, description, amount, type, status, source, installmentNumber, installmentTotal, notes`.

- `TransactionType`: `INCOME, EXPENSE`.
- `TransactionStatus`: `PENDING (default), PAID, CANCELED`, **nullable desde a V8** (`make_transactions_status_nullable`) — lancamentos `INCOME` sao sempre gravados com `status = null` (ver "Regras"); `EXPENSE` sempre tem status nao-nulo.
- **`categoryId` e obrigatorio no request desde a issue #45** (`@NotNull`, "A categoria é obrigatória."), mas a **coluna continua nullable**: lancamentos legados gravados sem categoria seguem existindo no banco e sendo listados. Nao houve backfill — o saneamento e gradual (DEC-2 da issue #45): editar um lancamento legado so passa depois de escolher uma categoria.
- `TransactionSource`: `MANUAL (default), EXCEL_IMPORT, RECURRENCE` — as duas ultimas indicam features de import/recorrencia **ainda nao implementadas**: o schema (`import_batches`, `import_rows`, V1) existe mas nao ha pacote/entidade Java correspondente ainda. Se uma issue pedir import de Excel ou recorrencia, isso e feature nova do zero, nao ajuste de algo existente.
- **`accountId`/`cardId` nao existem mais** (removidos na V7 — colunas dropadas, campos tirados dos DTOs/entidade): lancamentos nao tem mais nenhum vinculo com Conta ou Cartao, nem no banco nem na UI. Nao reintroduzir sem confirmar com o dono do produto; o vinculo historico ja gravado foi perdido de forma intencional.

## Regras

- **Campos obrigatorios de `TransactionRequest`** (mesmo DTO no `POST` e no `PUT`): `categoryId`, `transactionDate`, `description`, `amount` e `type`, todos com mensagem em portugues acentuado; `status`, `source`, parcelas e `notes` continuam opcionais no DTO (`status` tem regra propria, ver abaixo). A frase agregada sai na ordem de `FieldLabels`: "Informe os campos obrigatórios: Descrição, Valor, Data, Tipo, Categoria.".
- `amount >= 0.01` (`@DecimalMin`, mensagem "O valor deve ser maior que zero." desde a issue #45 — e a que o usuario ve, ja que o formulario nasce com `amount = 0` e nunca envia o campo nulo; o `@NotNull` mantem "O valor é obrigatório.", que alimenta a frase agregada) + constraint no banco `amount >= 0`; `installmentNumber`/`installmentTotal` `>= 1` se presentes, mas **nada valida `installmentNumber <= installmentTotal`** nem que os dois venham juntos — ponto de atencao se uma tarefa mexer em parcelamento.
- **`status` obrigatorio so para despesa** (issue #45, DEC-4): a checagem esta em `TransactionResource.validateStatus` (400 "O status é obrigatório."), **nao** como `@NotNull` no DTO — um `@NotNull` quebraria toda receita, que e gravada com `status = null`. Efeito colateral: para `EXPENSE` vinda da API o default `PENDING` do `apply()` ficou inalcancavel.
- **`status = null` para receitas**: `TransactionResource.apply()` (compartilhado por `POST /transactions` e `PUT /transactions/{id}`) forca `status = null` quando `type == INCOME`, independente do que vier no request; para `EXPENSE`, mantem o `status` recebido (que agora nunca chega nulo, ver acima) ou usa `PENDING` como default. `DELETE /transactions/{id}` (cancelamento) continua gravando `status = CANCELED` mesmo para receitas, sem excecao — e o unico caso em que uma receita fica com status nao-nulo.
- **Sem hard delete**: `DELETE /transactions/{id}` so muda `status` para `CANCELED` (cancelamento, nao remocao); transacoes canceladas continuam consultaveis e ate editaveis (ver "Frontend", reativa ao salvar) e saem dos totais do dashboard — mas **continuam contando como periodo disponivel** em `GET /dashboard/periods` (issue #69): um ano cujo unico lancamento esta `CANCELED` aparece no seletor de Ano/Mes do Resumo e e aceito pela validacao do resumo, senao o registro ficaria inalcancavel pela tela.
- **`GET /transactions` e paginado** (issue #87, padrao em [backend-patterns.md](backend-patterns.md)), sempre escopado pelo `userId` logado (`search(userId, TransactionFilter)`), filtros `description` (contem, sem caixa/acento), `categoryId`, `type`, `status`, `startDate`, `endDate` combinados por E; ordem data desc, `createdAt` desc, `id`. `GET /transactions/{id}` usa `findByUserAndId` (lancamento de outro usuario = 404).
- **Validacao de categoria no backend** (`TransactionResource.validateCategory`, POST e PUT): alem de obrigatorio (ver "Campos"), o `categoryId` informado precisa (1) existir (400 "Categoria informada não existe."), (2) ser do mesmo tipo do lancamento (400 "A categoria deve ser do mesmo tipo do lançamento.") e (3) estar ativa — excecao (issue #20): no PUT, categoria **inativa** e aceita se for a mesma ja gravada no lancamento, para permitir salvar a edicao sem trocar de categoria. Continua **sem** checagem de posse por usuario (categorias sao catalogo global, ver [categories.md](categories.md)).
- **`status = CANCELED` nao entra via POST/PUT** (`TransactionResource.validateStatus`, 400 "O status Cancelado só pode ser aplicado pelo cancelamento do lançamento."): cancelar e so via `DELETE /transactions/{id}`. Excecao: no PUT, `CANCELED` e aceito se o lancamento ja esta cancelado (o select de edicao do frontend pode reenviar o status atual sem o usuario mexer). Para `INCOME` a checagem nao se aplica — `apply()` forca `status = null` de qualquer forma.
- **As tres recusas de 400 do POST/PUT deixaram de ser indistinguiveis para o front** (issue #39): categoria inexistente, tipo incompativel e `CANCELED` via POST/PUT agora chegam ao Angular **com a mensagem no corpo** (`BusinessExceptionMapper`, ver `knowledge/backend-patterns.md`), que a tela exibe como toast de Alerta — antes o mesmo status cobria os tres motivos com corpo vazio, e nao havia fallback correto possivel.
- `PUT /transactions/{id}` (`TransactionResource.update`) reaproveita o mesmo `apply()` do `POST`, protegido por `accessControl.require(Screen.TRANSACTIONS, Action.EDIT)`; e o endpoint da edicao no cadastro `transaction-form` (ver "Frontend").

## Frontend (`frontend/src/app/features/transactions/`)

- **Listagem + cadastro em tela propria** (issue #87, padrao comum em `knowledge/frontend-ui.md`; a edicao inline e o formulario lateral acabaram). A listagem filtra Descricao, Categoria, Tipo, Status (sem padrao) e Data de/ate; o filtro Categoria usa o catalogo completo (inativas com "(Inativo)"), restrito ao Tipo do filtro. Por linha: "Editar" e o "Cancelar" (`.danger-button`, `DELETE` -> `CANCELED`). `<colgroup>` com Valor 130px (cabe `- R$ 12.480,00`). Um lancamento `CANCELED` pode ser editado e reativa ao salvar — intencional.
- **Nome da categoria na linha** vem do `categoryName` do proprio `TransactionResponse` (lista, detalhe, POST e PUT; nome gravado, inclusive de categoria inativa; `null` so sem `categoryId`, que a coluna mostra como "Sem categoria") — issue #89, padrao em [backend-patterns.md](backend-patterns.md). A listagem funciona com `TRANSACTIONS/VIEW` sozinho: o catalogo `GET /categories/options` sem `type` so alimenta o filtro Categoria, que fica oculto sem `CATEGORIES/VIEW` (ver `knowledge/frontend-ui.md`).
- **Cadastro `transaction-form`** ("Novo/Editar lançamento"): o dropdown de Categoria e filtrado pelo `type` via `GET /categories/options?type=` (`CategoryService.listByType`, so ativas); trocar o tipo com categoria incompativel selecionada limpa a selecao. O backend valida a mesma combinacao (ver "Validacao de categoria no backend") — o filtro e so a face visivel da regra. Valores iniciais: data de hoje, descricao vazia, valor 0, Despesa, Pendente, Categoria "Selecione". Payload `{...form, amount: Number, status: INCOME ? null : status, categoryId: '' -> null}`. **Sem `CATEGORIES/VIEW`** (ou com 403 do `/options`) o cadastro nao chama `/categories/options` nem `/categories/{id}` e mostra no lugar do dropdown "Seu perfil não tem permissão para ver Categorias, por isso não é possível escolher a categoria.", sem toast (issue #89): na edicao o `categoryId` gravado segue no PUT enquanto o Tipo nao for trocado (trocar limpa, e o back-end responde 400 "A categoria é obrigatória."); na inclusao o POST sempre volta esse 400 — sem ver Categorias nao se inclui lancamento (decisao da #89).
- **A opcao vazia do dropdown de Categoria e um placeholder "Selecione"** (issue #45), no lugar da antiga "Sem categoria". O `<option value="">` existe de proposito, para o estado vazio ser alcancavel e a validacao do backend observavel: o `required` do `<select>` e so espelho de UX e **nao bloqueia o submit** (o POST sai com `categoryId: null` e volta o 400).
- **Categoria inativa ja gravada no lancamento** (issue #20): na edicao, se ela nao esta entre as ativas do tipo, e resolvida por `GET /categories/{id}` e fixada em `preselectedInactiveCategory` como `<option>` extra "Nome (Inativo)" — permite salvar sem trocar; some ao trocar a categoria ou o tipo.
- O campo Status some do cadastro quando `type = INCOME` (espelhando a regra de backend acima); para `EXPENSE` oferece so "Pendente"/"Pago" (nunca "Cancelado" como opcao escolhivel).
- Status e sempre exibido traduzido (`transactionStatusLabel()` em `core/formatters.ts`): `PENDING -> "Pendente"`, `PAID -> "Pago"`, `CANCELED -> "Cancelado"`; nenhum valor cru do enum aparece na UI. Desde a issue #35 ele e renderizado como `status-pill` (`statusPillClass()`: verde para Pago, amarelo para Pendente, neutro nos demais) e a coluna Valor usa `signedMoney()`, com prefixo `+ `/`- ` e cor semantica por tipo — helpers **so de apresentacao**, sem efeito em fluxo ou HTTP.
- **Homonimos**: o "Cancelar" da **tabela** cancela o lancamento (`DELETE`, status `CANCELED`); o "Cancelar" do **cadastro** so sai, com "Deseja sair sem salvar?" se houver alteracao, sem HTTP.
- **Destaque de campo invalido** (issue #45): um 400 com `violations[]` marca cada campo citado (`transactionDate`, `description`, `amount`, `type`, `status`, `categoryId`) com `invalid` + `<small class="field-error">` (`core/field-errors.ts`, ver `knowledge/frontend-ui.md`); o foco vai para o primeiro campo invalido **na ordem visual do formulario**, nao na do `violations[]`.
- Feedback: Sucesso "Lançamento salvo com sucesso." (inclusao), "Lançamento atualizado com sucesso." (edicao) e "Lançamento cancelado com sucesso." (tabela). Com a API fora do ar, lista e catalogo falham juntos e a de-duplicacao do `ToastService` mostra um card so (ver `knowledge/frontend-ui.md`).
